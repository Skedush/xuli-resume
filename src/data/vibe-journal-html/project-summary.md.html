经验汇总：VPN 代理项目 + Workflow 演进

整理时间：2026-05-29

一、VPN 代理项目

核心目标

搭建稳定可控的代理网络环境，核心是稳定性，不只是"能翻出去"。

优先级：

  1. OpenAI API → 稳定性 > 速度（低丢包、低重传、长连接稳定）
  2. Docker / npm / GitHub → 下载速度 > 稳定性

技术栈

技术 用途
VPS（Linode / Vultr） 代理出口
Tailscale 节点互联，构建私有网络
mihomo / Clash Meta 代理核心 + 分流规则
SSH 隧道 本地端口转发，访问远端面板

排查工具

curl -4 -L -o /dev/null https://proof.ovh.net/files/100Mb.dat   # 下载测速
iperf3 -c VPS_IP -R    # 反向 TCP 传输质量
ping VPS_IP            # 基础延迟（但不能完整反映 TCP 质量）

主要坑

1. VPS 选型

  • 日本节点不一定好，线路可能绕路、晚高峰拥塞
  • 必须实测：下载、上传、TCP 重传率、晚高峰表现
  • 不能只看机房位置，要看到本地运营商的回程线路质量

2. Tailscale

  • UDP 打洞不稳定，可能被迫走 DERP 中继，延迟上升
  • MTU 问题：Tailscale 虚拟接口（utun）MTU 可能需要调整
  • 删除 VPS 后注意注销 Tailscale 节点

3. mihomo 面板 Mixed Content

  • HTTPS 前端调用 HTTP 后端 → 浏览器拦截
  • 解决：直接访问 HTTP 后端 / 本地静态资源 / 改用 HTTP 面板

4. 网络架构

  • 双重 NAT（光猫拨号 + 路由器 WAN 上联）会导致 UDP 打洞失败
  • Wi-Fi 质量、路由器性能都会影响整体延迟

VPS 判断原则

如果 VPS 下载慢、丢包高、延迟高 → 不适合作为代理出口
OpenAI API 请求勉强可用，但 Docker 镜像下载体验差

推荐方向

稳定 VPS（实测线路质量好）
  + mihomo / sing-box
  + 精确 OpenAI 分流规则（ RULE-SET + DOMAIN-SUFFIX 兜底）
  + Tailscale 节点互联
  + SSH 隧道辅助管理
  + 定期测速和更换线路

二、Workflow 演进

原始问题

把 OpenCode 和 Codex 当成"简单 worker"和"复杂 worker"的分工，Hermes 只做分发。

GPT 指出的问题：

  1. Hermes 被低估，降格成了 thin router
  2. OpenCode 推理弱但上下文大，适合做 context collector
  3. Codex 高推理，应该当专家用，不是更强的 worker
  4. 缺少质量门控

最终角色定义

角色 定位
Hermes Leader / Architect / Product thinker / Reviewer
OpenCode Large-context reader + broad repo scanner + narrow executor
Codex High-reasoning expert + complex implementer + reviewer

核心流程

Human goal + constraints
  ↓
Hermes context recall + bounded task
  ↓
OpenCode context packet（如需 repo 扫描）
  ↓
Hermes refined brief
  ↓
Codex expert review / implementation
  ↓
Hermes validation + final review

任务路由

  • Context-heavy（扫描文件/日志）→ OpenCode 先
